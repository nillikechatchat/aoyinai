## 一、只会说话的模型，办不了事

大模型的知识停在训练那一刻。它不知道你的库存还剩几件，也读不到今天的数据库，更无法替你发一封邮件。所谓「工具调用」（Function Calling，又称 Tool Use），要解决的正是这件事：把外部能力以结构化的接口「声明」给模型，让它在需要时主动开口调用。

《荀子》有言：「君子生非异也，善假于物也。」模型本身的智力或许固定，它能借用的工具却可以无限扩展。一个会调用搜索、数据库、计算器的普通模型，往往比一个只会空谈的更强模型更管用。

但很多人的第一课就走偏了：以为这只是「API 传参」——把函数写出来、把 schema 贴上去，就完事。真正的难点从来不在接口怎么写，而在判断：什么时候该调用、该调用哪一个、参数该填什么。这三件事都交给了模型，而模型的判断并不总是可靠。

## 二、三段式：声明、抉择、回填

一次完整的工具调用，永远是这三步在循环。理解了这个循环，再复杂的 Agent 都能拆开来看。

### 第一段：声明——把能力写成契约

你用 JSON Schema 描述工具的用途、参数与约束，随请求一起发给模型。例如一个查询天气的工具：

```json
{
  "name": "get_weather",
  "description": "查询指定城市当前天气。仅当用户询问天气时调用。",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "城市名，如「杭州」" },
      "unit": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}
```

请记住：`description` 不是注释，它是提示词。写得含糊，模型在该调用时沉默；写得具体（「仅当用户询问天气时调用」），它才听话。许多「模型不肯调用工具」的抱怨，根子都在这里。

### 第二段：抉择——模型只给出意图

模型不会真的执行工具，它只回一个结构化的「意图」：调哪个函数、参数是什么。这一步是整个链路的灵魂，也是坑最多的地方。你要接受一个事实：模型会选错工具、会漏参数、会编造不存在的字段。所以必须把它的输出当作「待校验的输入」，而非「可直接执行的命令」。

### 第三段：回填——把结果还给模型

你在本地执行真正的函数，把返回值以 tool 角色消息追加进对话，让模型基于真实数据继续作答。关键细节：工具返回要精简。把一整个庞大的 JSON 原样塞回去，往往换来一段啰嗦且容易出错的回答——上下文被稀释，重点被淹没。

## 三、工程上的四道坎

1. **描述即提示**：`description` 里写清「何时用」「何时别用」，比换更强的模型更有效；
2. **参数必校验**：模型输出的参数一律过 schema 校验，失败则带错误信息重试一次，绝不直接执行；
3. **结果要收敛**：工具返回值先做裁剪与摘要，必要时只回关键字段；
4. **循环要设限**：给「调用—回填」设最大轮数（如 5 轮），否则模型可能陷入死循环，一路烧钱。

其中第二道坎最容易被忽略。模型把 `"amount": "一百元"` 填进 numeric 字段是常事，直接执行就是事故。校验层不是可选项，它是工具调用的安全带。第三道坎则决定体验：一次查询返回上千行，不如让它返回一句「共 42 条，其中 3 条逾期」。

## 四、一个最小可用的循环

伪代码胜过千言：

```python
messages = [{"role": "user", "content": "杭州今天要带伞吗？"}]
for _ in range(5):
    resp = model.chat(messages, tools=TOOLS)
    call = resp.tool_call
    if not call:
        break
    args = validate(call.arguments)      # 参数校验，失败即重试
    result = dispatch(call.name, args)   # 本地执行真实函数
    messages.append(resp.message)
    messages.append({"role": "tool", "content": summarize(result)})
print(resp.content)
```

这段循环里没有任何魔法。工具调用的工程难度，全在 `validate` 与 `dispatch` 的边界上：前者挡住模型的幻觉，后者决定你能做什么。把这两处写扎实，Agent 的地基才算打好。

## 五、从单工具到多工具

当工具从一个变成十个，新的问题就来了：模型可能反复调用同一个工具、可能在错误的前提下调用、可能一次抛出多个互相依赖的调用。这时考验的已是你对任务的拆解能力，而非对 API 的熟悉程度。先规划再执行、给工具分组、明确调用顺序，甚至让另一个模型专职「调度」，都是常见的编排策略。工具越多，越要克制——每多一个工具，模型选错的概率就多一分。

## 六、结语

工具调用是把大模型接入真实世界的第一个接口，也是 Agent 的起点。它并不神秘，只是把分工线划得很清楚：模型负责判断，工程负责确定。

> 善假于物者，方能致远。工具调用，是模型学「借力」的第一课。
