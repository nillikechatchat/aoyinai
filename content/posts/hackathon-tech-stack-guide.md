## 技术选型决定你死在哪一晚

黑客松最常见的失败模式不是创意不行，而是**技术栈不熟，最后几小时耗尽在 Debug 上**。

48 小时能写多少代码是有限的，但踩坑的成本是无限的。选型的第一原则：**选你团队最熟的东西，而不是最炫的东西。**

## 选型三原则

### 1. 熟 > 新

评审不会因为"用了最新框架"加分，但会因为"演示崩溃"扣大分。团队里谁最熟什么，就用什么。选型会议 10 分钟内定不下来，直接投票选"团队里有人写过超过 3 个项目的方案"。

### 2. 少 > 多

技术栈越少，变量越少。一条主链路里尽量只出现 2-3 种关键技术，其余全部用成熟服务兜底。每多一个组件，就多一分"当晚装不上、跑不动"的风险。

### 3. 有兜底 > 无兜底

每个关键环节都要想好"如果它挂了，我怎么降级"。AI 调用失败时的 fallback、数据库不可用时的本地文件、演示现场的断网预案，都应该在选型阶段就留好后路。

## 前端选型

黑客松前端要的是**快**和**稳**：

- 有前端经验团队：React/Vue + 现成组件库（Ant Design、Tailwind UI），优先模板起步
- 无前端经验的 AI 团队：直接选低代码/组件化方案，或用纯 HTML + 现成组件库
- **永远不要在黑客松现场手搓样式**

表单、表格、聊天界面都有成熟组件，直接组装，把时间留给核心逻辑。

## 后端与数据

- 简单应用：Node.js 或 Python（FastAPI / Flask），一个文件启动
- 需要数据库：SQLite 起步，上线再换 PG；不要一上来就配集群
- 需要队列/异步：先用进程内任务，别急着上消息队列

**关键原则：能用文件就用文件，能用单机就用单机，能同步就别异步。** 黑客松的目标是"演示能跑"，不是"架构优雅"。

## AI 能力接入

2026 年多数黑客松都会用到大模型能力，选型上注意三点：

1. **用成熟 API 优先**：先接托管 API 跑通闭环，再考虑本地模型
2. **给 AI 调用加超时与重试**：现场网络抖动是最大隐患，必须有 fallback 文案
3. **预置缓存**：演示高频路径提前缓存结果，避免现场反复调用导致延迟

记住：**演示现场，AI 慢就是 AI 挂了**。所有关键路径都要准备好"降级也能演完"的方案。

## 部署与演示预案

- 提前一天把应用部署到公网可达的地址，演示用线上地址而非本地
- 准备断网兜底：关键截图、录屏、缓存好的演示视频
- 现场环境提前一天确认（电源、网络、投影转接头），这些琐事杀死过最多的演示

## 一份参考栈

- 全栈模板：Next.js + Tailwind + Vercel，AI 调用走托管 API
- Python 团队：FastAPI + 前端模板 + 托管部署
- 纯工具型 Demo：现成组件库拼装 + 后台逻辑

**这套组合的核心是一个"最小可演示闭环"：用户操作 → 后端处理 → AI 生成 → 结果展示，全程 2-3 个技术组件。**

## 总结

黑客松技术选型的本质，是把"交付稳定性"置于"技术先进性"之上。48 小时里，稳定跑完 Demo 是 100 分，炫酷但崩溃是 0 分。

选最熟的栈、砍最少的组件、备好降级方案，然后把省下来的时间花在打磨故事和演示上——这才是 48 小时交付的王道。
