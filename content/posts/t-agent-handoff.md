## 一、失败发生在两张工位之间

Planner 说「去把销售数据洗一下」，DataProcessor 洗了全量，含测试账号，Reporter 据此画出一条假趋势。两边都觉得自己完成了任务。单体 Agent 把这种错藏在长上下文里；多智能体把它暴露在交接面上——这是好事，前提是你真的定义了面。

《论语》说「不在其位，不谋其政」。也要补一句：在其位，必须把政交清楚。

## 二、一份最小交接单

每条任务消息固定字段：

```json
{
  "task_id": "T-1842",
  "goal": "清洗 2025 年成交订单，排除测试账号",
  "input_ref": "s3://.../orders.parquet",
  "constraints": ["customer_id 不得出现在输出", "时区 Asia/Shanghai"],
  "done_when": ["行数对照表", "空值率 < 1%"],
  "on_fail": "退回 Planner，附样本 5 行"
}
```

`done_when` 是验收，不是愿望。没有它，下游只能用「看起来像」来判断完成。

Worker 有拒绝权：输入对不上、约束冲突、工具权限不足，必须退回，禁止「尽量做」。尽量做是事故的温床。

## 三、三次事故

1. **隐式默认**：没写时区，Worker 用 UTC，报表差 8 小时。此后时区成为必填。
2. **过大输入**：把 200MB JSON 塞进消息。交接只传引用（路径、ID），正文放对象存储。
3. **口头加塞**：有人在聊天里让 Worker「顺便」改口径。顺便绕过了协议，审计账本出现缺口。我们后来禁止旁路指令，一律进消息总线。

## 四、协议要版本化

字段增减按版本号。旧 Worker 遇到新字段可忽略，遇到不认识的必填则拒绝。滚动升级时，Planner 先发双版本，观察拒绝率再切。

人读的说明和机读的 schema 放在同一仓库。只写 wiki、不写 schema，等于没有协议。

> 礼者，天地之序也。交接协议是多智能体的礼。
