## Agent 失控是概率问题，不是科幻问题

2026 年多智能体系统进入生产后，安全问题从"会不会发生"变成"怎么处理"。Agent 可能因为提示词注入、工具误调用、上下文越权做出越界操作——**单个 Agent 的失误，会通过工具链和委派链被放大**。

安全设计的核心思路和传统系统不同：不是假设 Agent 可靠，而是假设 **Agent 随时可能出错**，通过架构层限制它的能力边界。

## 第一道防线：权限最小化

### 身份隔离

不要让所有 Agent 共享同一个"超级身份"。每个 Agent 应绑定独立的最小权限身份，遵循**最小权限原则**：只能访问完成自己任务必需的资源。

典型场景：写代码的 Agent 不该有生产数据库的写权限，搜索的 Agent 不该能读内部文档。

### 资源边界

从四个维度限制 Agent 的能力：

- **网络**：Agent 能访问哪些域名、端口
- **文件系统**：能读写哪些目录
- **数据库**：能访问哪些库、哪些表
- **外部 API**：能调用哪些服务、额度多少

把边界做成**显式配置**而不是默认放开，是防住绝大多数越权操作的前提。

## 第二道防线：工具调用管控

工具是 Agent 能力的放大器，也是风险放大器。三层管控：

### 1. 工具分级

按风险程度把工具分成三级：

- **低风险**（搜索、计算、格式化）：Agent 可自动调用
- **中风险**（发邮件、写文件、更新数据）：需要审批或记录
- **高风险**（转账、删除、生产变更）：强制人工审批

### 2. 参数校验

Agent 生成的参数可能"合理但越界"。在工具执行前加校验层：金额上限、目标范围、操作白名单。**工具执行器要校验参数，不能盲目信任模型输出。**

### 3. 调用审计

所有工具调用记录完整审计日志：谁调的、传了什么参数、结果是什么。审计日志是事后追责和攻防分析的基础，也是合规的硬要求。

## 第三道防线：数据治理

### 数据分级

把数据按敏感度分级，写入 Agent 的访问策略：

- **公开数据**：所有 Agent 可访问
- **内部数据**：需授权的 Agent 可访问
- **敏感数据**：严格白名单，且需要审批

### 输出管控

Agent 输出可能携带敏感信息。在生产链路加**输出过滤**：检测返回内容是否包含手机号、身份证、内部系统名等敏感信息，命中即拦截或脱敏。

### 上下文隔离

多 Agent 共享上下文是常见的数据泄露点。确保每个 Agent 只能看到自己任务范围内的数据，**防止通过委派链把敏感数据传递给低权限 Agent**。

## 针对提示词注入的专项防御

提示词注入（Prompt Injection）是 Agent 特有的攻击面。三道防御：

1. **输入消毒**：用户输入与系统指令分隔存放，防止注入内容覆盖系统规则
2. **指令优先级**：在代码层（而非纯 prompt）强制执行高优先级约束，不依赖模型自觉
3. **工具层护栏**：即使 prompt 被注入，工具执行器仍按权限和校验规则执行——**最后的防线在工具层，不在模型层**

## 一整套安全清单

上线前用这份清单自检：

- [ ] 每个 Agent 是否绑定独立最小权限身份
- [ ] 网络、文件、数据库、API 边界是否显式配置
- [ ] 高风险工具是否有强制人工审批
- [ ] 工具执行器是否校验参数、记录审计日志
- [ ] 数据是否分级，Agent 能否访问超范围数据
- [ ] 输出链路是否过滤敏感信息
- [ ] 关键约束是否在代码层强制执行

## 总结

多智能体安全的本质是**纵深防御**：权限边界、工具管控、数据治理三层叠加，每层都假设上一层会被绕过。

最核心的一条原则：**永远不要把安全托付给模型本身。** 权限、审批、校验、审计这些机制必须在代码层落实，Agent 的能力边界由架构决定，由模型发挥。
