## 为什么"感觉不错"会害了项目

在 AI 应用开发里，最常见的踩坑姿势是这样的：改了一版提示词，人工点了几条看起来不错，就上线了。结果线上真实用户的输入分布跟你的"看起来不错"完全不同，效果直线下滑。

**人类的主观抽检无法代表真实效果。** 它的样本量太小、选样有偏、而且无法重复。真正的工程化做法，是把"效果好坏"变成一组可以反复运行的量化指标——这就是 LLM 评测（Evals）。

评测不是"打分的玩具"，它解决三个实际问题：

1. **回归防护**：提示词、模型、检索逻辑任何一次改动，都可能悄悄让效果变差。评测集能在改动后立刻报警。
2. **选型依据**：换模型、调参数，效果是变好还是变坏，用分数说话而不是感觉。
3. **优化方向**：哪些场景持续拉低分数，评测结果能告诉你下一步该修哪里。

## 第一步：建一份"像真实用户"的评估集

评估集是评测的地基，它的质量决定评测的可信度。核心原则：**评估集要反映真实用户输入，而不是你想要的效果**。

### 收集来源

- **线上日志**：真实用户输入是最高价值来源，脱敏后抽样
- **人工构造**：针对边界情况手写，比如空输入、长文本、生僻术语、恶意输入
- **社区与历史数据**：工单、客服记录、历史问答

### 规模建议

不用贪多。一份覆盖主要场景的评估集，**30~80 条**往往就够日常回归；需要做正式效果验收时再扩展到几百条。

关键在覆盖度，不在数量：

| 维度 | 例子 |
| --- | --- |
| 正常场景 | 常见问题的标准答案 |
| 边界场景 | 超长输入、空输入、单字输入 |
| 困难场景 | 专业术语、歧义句、多轮追问 |
| 负面场景 | 诱导输出、越权请求、幻觉风险 |

### 标注与拆分

每条评估样本应包含：输入、期望行为（参考答案或标准）、通过标准。数据要**脱敏**。拆成两部分：训练时参考的调试集，和不动、只用来回归的冻结集。

## 第二步：选评估指标

根据任务类型选择打分方式，没有放之四海皆准的指标。

### 自动指标

- **LLM 作为裁判（LLM-as-Judge）**：用一个更强的模型对输出打分。适合开放任务，比如"回答是否准确、是否完整、是否友好"
- **规则匹配**：输出是否包含关键字段、是否符合格式。适合结构化任务，比如 JSON 校验、必含术语
- **语义相似度**：输出与参考答案的向量相似度，粗粒度参考，不推荐单独使用

### 人工标注

自动指标无法覆盖所有维度，特别是"专业性"和"价值观"这类需要人判断的。正式验收阶段，抽 50~100 条做人工二分类（通过/不通过）是低成本高价值的手段。

**实践建议**：日常回归用自动指标全量跑，发布前做一轮人工抽检，两层配合。

## 第三步：写一个可重复运行的评测脚本

评测要能反复跑，就必须是脚本而不是手工。一个最小实现：

```python
import json
from judge import judge_response  # 你的 LLM 裁判逻辑
from my_app import run_agent  # 你的应用入口

CASES = json.load(open("eval_cases.json"))

def evaluate():
    results = []
    for case in CASES:
        output = run_agent(case["input"])
        passed, reason = judge_response(case, output)
        results.append({"input": case["input"], "output": output, "passed": passed, "reason": reason})

    passed_count = sum(1 for r in results if r["passed"])
    return passed_count / len(results), results

pass_rate, results = evaluate()
print(f"通过率：{pass_rate:.1%}")
```

把这个脚本固定下来，每次改动后运行一次，把结果存下来对比。

## 第四步：把评测变成开发流程的一部分

有了脚本，接下来是让它真正保护项目：

### 建立基线

第一次运行的结果记为基线。之后任何一次改动（提示词、模型、检索、参数）都对比基线。

### 回归测试

在代码仓库里加一条 CI 任务：改动合并前跑评测，通过率下降超过阈值（比如 2%）就阻止合并。**让效果回归像代码回归一样被拦截。**

### 持续扩充

每次线上出现重大效果问题，把出问题的输入补充进评估集。评估集是项目的资产，会越用越准。

## 常见误区

- **评估集太小且固定不变**：十几条样本无法反映分布，且要持续补充真实案例
- **指标与目标错位**：明明在意"专业术语准确"，却只打"流畅度"分
- **评测集与调试集混用**：用训练过的样本测回归，会得到虚假的高分
- **只测通过率不看案例**：分数是信号，具体失败的样本才是原因

## 一个可以立刻开始的方案

不需要一开始就搭完整体系，从最小闭环开始：

1. 从你的应用里挑 40 条真实输入，标注期望行为
2. 写一个 30 行的评测脚本，用 LLM 裁判打分
3. 跑出基线通过率
4. 下一次你"觉得效果变好了"时，用脚本验证一下

当你发现"脚本结果和你的直觉冲突"的那一刻，评测体系的真正价值就体现出来了——它会纠正那些凭感觉做的决定。

## 总结

AI 应用评测的本质，是**把"效果"从主观感受变成可重复验证的工程资产**。一份像真实用户的评估集、一套分场景的指标、一个能反复运行的脚本，就构成了最小可行评测体系。

先跑起来，再逐步完善。评测不是一次性的工作，它是伴随应用生命周期的持续投资。
