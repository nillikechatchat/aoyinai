## Agent 系统的失败模式不一样

传统服务的故障通常是确定性的：某个接口超时、某条 SQL 慢。多智能体系统的故障则完全不同——**没有报错，只是结果不对**。Agent 可能调用错了工具、循环了 30 轮、上下文被污染，但进程没有崩溃，日志里全是正常输出。

这就是 Agent 生产化最大的坑：**没有可观测性，就没有排查入口**。很多团队把 Agent 上线后才发现，出了问题根本不知道从哪查起。

## 传统监控为什么不够

传统监控三板斧——指标、日志、告警——在 Agent 系统里都会失效：

- **指标**：响应延迟、错误率看不出 Agent 内部的决策质量
- **日志**：Agent 一轮对话会产生大量中间过程日志，噪声远大于信号
- **告警**：Agent 不会崩溃，传统告警规则几乎不会被触发

Agent 系统需要的是**过程级可观测性**：不仅知道"结果是什么"，还要知道"Agent 中间做了什么决策、走了哪条路径、为什么是这个结果"。

## 三层可观测设计

### 第一层：链路追踪（Trace）

把一次完整的 Agent 任务看作一条链路，记录其中每个环节：

- 模型调用：prompt、响应、Token 数、延迟
- 工具调用：工具名、入参、返回摘要、耗时
- 子 Agent 调用：委派了谁、返回了什么
- 状态流转：每一步的 state 变化

用 trace 能把"用户问题 → 最终回答"之间的所有步骤串起来。这是排查的第一步——**先定位问题出在哪个环节**。

### 第二层：状态快照（State Snapshot）

Agent 的状态（上下文、记忆、待办、中间结果）是排查的关键。在关键节点打快照，记录：

- 当前上下文长度与内容摘要
- 记忆检索命中了什么
- 循环次数与迭代历史
- 关键决策点的输入输出

状态快照让你能**重现 Agent 当时的视角**，判断是上下文污染、记忆误召回，还是决策逻辑本身有问题。

### 第三层：评估反馈（Evaluation）

可观测性不只是"看"，还要"自动判断好不好"。把评估集成进生产链路：

- 对每次 Agent 输出跑自动评估（正确性、相关性、安全性）
- 记录评估分数随时间的趋势
- 低分样本自动进入回放队列，用于后续迭代

这一层把"排查事故"升级成"持续度量质量"。**没有评估的生产 Agent，等于盲飞。**

## 落地方案选型

### 开箱即用的托管平台

LangSmith、Langfuse 这类平台提供 trace、回放、评估一体化的能力，接入成本低，适合快速落地。核心收益是**开箱即用的链路追踪与回放**。

### 自建方案

如果数据敏感或需深度定制，用 OpenTelemetry 基础 + 自建存储。常见组合：

- Trace 数据用 OTLP 协议上报，存 OpenSearch / ClickHouse
- 状态快照存对象存储，按任务 ID 检索
- 评估用离线批处理 + 在线采样

### 关键点：统一任务 ID

不管用哪种方案，**在入口生成唯一的任务 ID，并贯穿整条链路**（模型调用、工具调用、快照、评估结果都带上）。没有统一 ID，trace 就串不起来。

## 一个可执行的落地顺序

1. **先加 Trace**：接入托管平台或自建，先把"任务 → 环节"串起来，当天就能用
2. **再加快照**：在关键决策点打状态快照，解决"重现现场"问题
3. **最后加评估**：选一个业务指标跑在线评估，建立质量基线

顺序上先解决"能看"再解决"能判"。不要一上来就追求完整的评估体系，那会把落地拖得很久。

## 总结

多智能体系统的可观测性，核心是回答三个问题：**它做了什么、当时状态是什么、做得怎么样**。分别对应链路追踪、状态快照、评估反馈三层能力。

Agent 生产化的分水岭就在可观测性上。能看清 Agent 每一步行为的团队，和只能对着最终输出猜的团队，迭代速度差一个数量级。
