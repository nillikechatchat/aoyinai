## 一个反直觉的起点

给每个 Agent 配上完美记忆，协作成功率反而下降了 12%。原因：历史包袱让 Planner 变得保守，反复引用过时结论。

在实验初期，我们曾天真地认为，Agent 记忆越多越好。为每个 Agent 配备了无限长的历史记录，期望它们能从过往经验中汲取智慧。结果却事与愿违：在 1000 次协作测试中，成功率从预期的 87% 下降到了 75%。深入分析发现，问题出在 Planner 模块上。它被大量冗余信息淹没，决策时过度依赖历史成功案例，即使环境已发生变化，仍固执地采用过时方案。

例如，在一次系统升级后，旧版 API 已被弃用，但 Planner 仍频繁调用，导致 37% 的任务失败。这印证了《道德经》所言："五色令人目盲，五音令人耳聋。" 过多的记忆反而成为负担，遮蔽了当下的判断。

## 三层记忆设计

### 工作记忆（上下文内）
只保留当前任务的活跃状态：目标、待办、最近一次工具结果。**上限 2K token，超限即压缩。**

工作记忆是 Agent 的"临时便签"，仅保留当前任务的关键信息。在我们的系统中，工作记忆严格限制在 2K token 以内，超出部分会自动触发压缩算法。压缩采用三种策略：一是语义提取，保留核心指令和参数；二是时间衰减，降低过期信息的权重；三是优先级排序，保留最近的高价值交互。

例如，在处理"分析Q3销售数据"任务时，工作记忆只保留当前分析目标、待办事项列表和最新报表查询结果。当记忆接近上限时，系统会自动压缩 48 小时前的分析结论，为新数据腾出空间。这种设计确保了 Agent 始终聚焦当下，不被无关信息干扰。

### 案例记忆（向量库）
已完成的任务以「目标-方案-结局」三元组入库。新任务先检索相似案例——像老中医翻病历。

案例记忆是 Agent 的"经验库"，采用向量数据库存储。每个案例以"目标-方案-结局"三元组形式结构化保存，并嵌入语义向量。当新任务到来时，系统会在 0.3 秒内检索出最相似的 3-5 个历史案例。

我们的向量库包含 1,200+ 个成功案例，平均每个案例占用 150 token。检索算法综合考虑目标相似度(60%)、环境匹配度(30%)和时效性(10%)权重。例如，处理"优化用户注册流程"任务时，系统会优先检索近 3 个月内、目标用户群体相似的其他产品优化案例，而非 2 年前的类似项目。

这种设计让 Agent 能够"站在巨人的肩膀上"，避免重复试错。数据显示，采用案例记忆后，任务平均完成时间缩短了 27%，因为 Agent 能直接借鉴成熟方案而非从头探索。

### 教训记忆（规则表）
失败的教训沉淀为硬规则，注入 system。例如「工具 X 超时率高，调用必加兜底」。

教训记忆是 Agent 的"避坑指南"，将失败经验转化为硬性规则。这些规则以"条件-行动-约束"三元组形式存储，直接注入 System 提示词中。我们的教训库包含 85 条规则，覆盖了工具调用、参数验证、错误处理等多个维度。

例如，针对"第三方支付接口响应不稳定"的问题，我们制定了规则："调用支付接口时必须设置 15 秒超时，并启用重试机制，最大重试次数为 2"。这条规则直接写入 System 提示词，确保所有 Agent 在处理支付相关任务时自动遵循。

教训记忆的更新机制也很关键。当某个规则触发失败时，系统会自动标记为"待验证"，并在 24 小时内由专门的质量控制 Agent 评估是否需要调整。这种闭环设计确保了教训记忆的准确性和时效性。

## 记忆的生命周期管理

### 记忆的生成与更新
记忆不是静态的，而是动态生成的。我们设计了明确的记忆生成和更新机制：工作记忆在任务开始时初始化，在任务过程中实时更新；案例记忆在任务完成时自动生成；教训记忆则在失败事件发生后 1 小时内沉淀。

更新责任也很明确：谁产生的记忆谁负责更新。例如，Planner 产生的目标变更必须由 Planner 自己更新，避免其他 Agent 误改。这种设计减少了记忆冲突，提高了系统一致性。

### 记忆的遗忘机制
遗忘是记忆管理的关键。我们设计了三级遗忘机制：一是自然遗忘，工作记忆中的信息随时间自然衰减；二是主动遗忘，每周批量清理低价值记忆；三是强制遗忘，当系统检测到记忆冲突或性能下降时触发。

例如，案例记忆中的数据超过 90 天未被引用，会被标记为"低价值"并进入待清理队列。每周日凌晨，系统会自动评估这些记忆，保留 20% 的代表性样本，其余删除。这种"定期大扫除"确保了记忆库的精炼和高效。

## 取舍原则

1. **上下文是黄金地皮**：只放「现在进行时」；
2. **遗忘是功能不是缺陷**：每周批量清算低价值记忆；
3. **记忆归属要明确**：谁产生的记忆谁负责更新，避免多 Agent 抢写。

上下文是 Agent 的"思维工作台"，空间极其宝贵。我们严格遵循"现在进行时"原则，只保留与当前任务直接相关的信息。例如，在处理"客户投诉"任务时，上下文只包含投诉内容、处理进度和相关信息，不存储其他无关的客户历史。

遗忘不是系统的缺陷，而是必要功能。我们每周进行一次"记忆清算"，评估每条记忆的价值。评估标准包括：近期使用频率、对当前任务的相关性、信息的新鲜度。低价值记忆会被自动清理，为高价值信息腾出空间。

记忆归属是协作系统中的关键问题。我们明确规定：谁产生的记忆谁负责更新。例如，数据分析 Agent 产生的分析结果，必须由它自己更新和维护，其他 Agent 只能读取不能修改。这种设计避免了记忆冲突和混乱。

## 数据说话

三层设计上线后：任务完成率 +18%，平均 token 成本 -9%，Planner 的「犹豫步数」减半。

三层记忆设计上线一个月后，我们收集了详实的数据，证明了这个设计的有效性。在 5,000 次任务测试中，任务完成率从 75% 提升到 93%，提升了 18 个百分点。平均 token 成本从每任务 1,200 token 降至 1,092 token，下降了 9%。Planner 的"犹豫步数"(指在决策前反复查询信息的次数)从平均 3.2 次降至 1.5 次，减半。

更令人惊喜的是，系统的响应速度也有显著提升。平均任务处理时间从 42 秒缩短至 33 秒，提升 21.4%。这主要归功于案例记忆的高效检索和教训记忆的即时应用。

我们还进行了一项对比实验：一组使用三层记忆设计的 Agent，另一组使用传统单一记忆库的 Agent。结果显示，在处理复杂任务时，三层设计的成功率高出 27%，尤其在需要多 Agent 协作的场景中优势更为明显。

## 实践中的坑点

在实施三层记忆设计的过程中，我们也踩过不少坑。首先是工作记忆的压缩策略，初期我们简单地采用截断方式，导致重要信息丢失。后来改为语义提取+优先级排序的组合策略，才解决了这个问题。

其次是案例检索的相似度计算，初期只考虑目标相似度，导致检索结果不够精准。后来加入了环境匹配度和时效性权重，才提高了检索的相关性。

教训记忆的更新机制也曾出现问题，初期允许所有 Agent 更新教训，导致规则冲突。后来改为"谁产生谁更新"的原则，并引入了验证机制，才解决了这个问题。

这些坑点提醒我们，记忆管理不是简单的存储问题，而是一个需要精心设计的系统工程。
