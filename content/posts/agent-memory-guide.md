## 一、为什么你的 Agent 健忘

大模型本身无状态。每一次调用都是初见——除非你把「过去」装进上下文。记忆系统的本质，是决定**什么值得被记住、何时被想起**。

实践中，我们见过太多 Agent 在多轮对话后突然「失忆」。用户提到上周的订单状态，Agent 却表示「初次见面」；要求修改之前设定的参数，Agent 却坚持「默认设置」。这种健忘不仅降低用户体验，更让 Agent 无法完成复杂任务。

《论语》有云：「温故而知新，可以为师矣。」一个不会回顾的 Agent，注定只能在原地打转。大模型的上下文窗口虽已扩展至 128K 甚至更高，但盲目填充所有历史对话，会导致「上下文污染」——重要信息被淹没在大量无关内容中，反而降低响应质量。

记忆系统的核心挑战在于：如何在有限的上下文空间内，高效存储和检索关键信息。这需要我们区分「短期记忆」（当前对话的即时信息）、「长期记忆」（用户偏好、历史行为等持久信息）和「工作记忆」（当前任务所需的临时信息）。没有这种区分，Agent 就像一个没有分类整理的仓库，找东西全靠运气。

## 二、三个递进实验

### 实验一：对话滑动窗口

保留最近 N 轮对话。五分钟实现，代价是「远期事项」静默丢失。适合闲聊，不适合办事。

实现滑动窗口记忆最简单直接。在代码层面，维护一个固定长度的队列，每次新对话进入，移除最旧的一轮。例如，设置窗口大小为 10，则只保留最近的 10 轮对话内容。

```python
# 伪代码示例
conversation_window = deque(maxlen=10)

def add_to_conversation(user_input, model_response):
    conversation_window.append({"user": user_input, "assistant": model_response})
```

这种方法的优势在于实现简单、计算成本低。在 GPT-3.5-turbo 中，我们可以轻松实现一个 10-15 轮的滑动窗口，而不会显著增加 API 调用成本。

然而，其缺陷也十分明显：当对话超过窗口长度，早期关键信息将永久丢失。例如，用户在第 2 轮提到「我住在上海」，在第 15 轪询问「明天上海的天气」，如果窗口大小为 10，Agent 已经忘记了用户的位置信息。

在实际应用中，滑动窗口适合客服、闲聊等不需要长期记忆的场景。但对于需要持续跟踪用户需求的任务，如项目管理、购物助手等，这种方法就显得力不从心。我曾见过一个客户服务 Agent，在用户描述完问题后，因为窗口滑动而丢失了关键故障代码，导致无法提供准确解决方案。

### 实验二：摘要压缩

每满十轮，用小模型把前文压缩成一段摘要塞进 system。上下文省了 70%，细节保不住——但方向对了。

当滑动窗口不再满足需求，摘要压缩成为进阶选择。其核心思路是：定期使用较小的模型（如 GPT-3.5 或专用压缩模型）对历史对话进行摘要，将压缩结果放入系统提示中，同时保留最近的几轮完整对话。

具体步骤如下：
1. 设置摘要触发点（如每 10 轮或达到一定 token 数量）
2. 调用压缩模型，提取关键信息并生成摘要
3. 将摘要加入系统提示，保留最近的 3-5 轮完整对话
4. 重复此过程

这种方法能节省约 70% 的上下文空间。例如，一个原本需要 8000 token 的对话历史，经过摘要压缩后可能只需要 2400 token 左右，为新的对话内容腾出空间。

然而，摘要压缩的代价是细节丢失。压缩模型可能会忽略看似不重要但实际关键的信息。例如，用户提到的特殊偏好、中间步骤的临时决策等，都可能被当作「冗余信息」过滤掉。

在实践中，我们尝试过不同的摘要策略：固定轮数摘要、基于内容重要性摘要、混合摘要等。其中，混合策略表现最佳——既考虑轮数，又评估内容重要性，同时保留用户明确标注「请记住」的信息。

《道德经》云：「少则得，多则惑。」摘要压缩正是体现了这一智慧——通过舍弃次要信息，保留核心要点，让 Agent 在有限的上下文中抓住重点。

### 实验三：向量记忆库

把关键事实（用户偏好、已完成的步骤、失败教训）写入向量库，按语义检索召回。这是长期记忆的正形。

当摘要压缩仍不能满足需求，向量记忆库成为终极解决方案。这种方法的核心是将重要信息提取为结构化事实，存储在向量数据库中，通过语义相似度检索相关记忆。

实现步骤如下：
1. 设计记忆提取提示，指导模型识别值得记忆的信息
2. 将提取的事实转换为向量（如 OpenAI embeddings）
3. 存储向量数据库，并附上原始文本和时间戳
4. 每次对话前，根据当前上下文检索相关记忆
5. 将检索结果与当前对话合并，发送给大模型

向量记忆库的优势在于：
- 精准检索：通过语义相似度而非简单关键词找到相关记忆
- 结构化存储：可以给记忆打标签、分类，便于管理
- 持久化：记忆可以长期保存，不随对话结束而消失
- 可扩展：可以轻松添加新的记忆类型和检索策略

在实际应用中，我们构建了一个三层记忆架构：
- 短期记忆：最近 3-5 轮对话
- 工作记忆：当前任务相关的临时信息
- 长期记忆：向量数据库中的结构化事实

例如，在个人健康管理 Agent 中，长期记忆可能包括：
- 用户的基本信息（年龄、性别、健康状况）
- 已知过敏原
- 既往病史
- 用户偏好（如不喜欢某种运动）
- 过往成功/失败的健康计划

每次对话时，Agent 会根据当前话题检索相关记忆。当用户询问「如何减脂」时，Agent 会检索到用户「有轻度高血压」的历史记录，从而避免推荐高钠饮食方案。

## 三、三条军规

1. **写入比读取更讲究**：不是所有话都值得记，让模型自己判断「此句可留」；
2. **记忆要会过期**：给每条记忆打时间戳与置信度，旧账定期清算；
3. **检索精度大于容量**：能精准想起十件事的 Agent，胜过糊涂记得一千件的。

### 写入比读取更讲究

记忆系统的质量，80% 取决于写入策略。盲目记录所有对话内容，会导致记忆库被「噪音」污染，反而降低检索效果。

有效的写入策略应包括：
- 重要性评估：设计提示词，让模型判断信息是否值得记忆
- 结构化提取：将非结构化对话转换为结构化事实
- 去重机制：避免记录重复或冲突的信息
- 上下文过滤：过滤掉临时性、偶然性的信息

例如，我们可以这样设计记忆提取提示：
```
以下是一段对话，请提取值得长期记忆的信息，以JSON格式返回：
{
  "facts": [
    {
      "content": "事实内容",
      "type": "preference|fact|preference|constraint",
      "confidence": 0.8
    }
  ]
}
```

在实践中，我们发现让模型参与记忆决策比硬编码规则更有效。模型能更好地理解语境，判断哪些信息可能在未来有用。例如，用户随口提到的「我不喜欢吃香菜」，虽然只是简单的一句话，但对餐饮推荐类 Agent 却至关重要。

### 记忆要会过期

记忆不是越多越好，过时的记忆会干扰当前决策。就像《大学》所言：「苟日新，日日新，又日新。」Agent 也需要定期「更新」自己的记忆。
