## 一、模型会按所有它够得着的按钮

给 Worker 一把「能跑 SQL」的钥匙，它迟早会写出 `DELETE`。不是因为它恶意，是因为提示词里出现了「清理」，而清理在 SQL 里是有歧义的。沙箱的职责是让歧义无法落地。

《周易》说「君子以慎辨物居方」。物是工具，方是权限边界。

![执纲振纪，众偶同台](/images/illu-t-agent.png)

## 二、最小权限

每个角色一张工具白名单。DataFetcher 只有 SELECT 与只读 API。Writer 类工具单独角色，默认关闭，需 Planner 签发一次性令牌。令牌绑定 `task_id` 与过期时间，用完即废。

参数再过一层：表名、路径、URL 域名走允许列表。模型拼出的 `../` 与内网地址，直接拒绝。

## 三、硬超时与并发

工具调用默认 8 秒，可按工具覆盖。超时返回结构化错误，不把半截 stdout 当成功。同一 Worker 并发上限 2，防止它在循环里打爆下游。

重试只对幂等工具开放。发送邮件、扣费、写工单，禁止自动重试。需要重试的，生成新的 `idempotency_key` 由人类或 Planner 确认。

## 四、副作用清单

每个工具在注册时声明：读 / 写 / 外部可见。外部可见（发信、发帖、对客回复）必须二次确认。我们曾让客服 Worker 直接调用「发送」，它把调试句子发到了真实用户——此后外部可见一律先入草稿队列。

差点写穿数据库的那次：迁移脚本被当成「工具」挂到了运维 Agent。现在迁移不进工具表，只进人工 runbook。

## 五、观测

每次调用记：角色、工具名、耗时、是否超时、是否被拒绝、task_id。拒绝率突然升高，优先查 schema 变更，查模型「变笨」。

> 防患于未然。未然就是工具还没碰到生产数据的那一层。
