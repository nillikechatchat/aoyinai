## 一、先把期望放低：多智能体解决什么问题，又不解决什么

如果你的印象来自演示视频，多智能体看起来像一支会自己开会的团队：规划者、执行者、评审者各司其职，最后交付一份漂亮的报告。真实工程里，失败往往出现在最不科幻的地方——A 把任务交给 B 时，双方对「完成」的定义不一样；C 调用工具时拿到了过期的数据；D 重试了三次，把同一笔订单下了三遍。

Anthropic 在 2024 年 12 月发布的《Building Effective Agents》里给过一条朴素建议：**优先用简单、可组合的工作流，只有在确实需要模型自主决策循环时才上智能体。** 这句话值得每个准备「上多智能体」的团队抄在墙上。多智能体带来的收益是分工与并行，代价是通信、状态与调试复杂度的指数上升。

《孙子兵法》讲「先胜而后求战」。上多智能体之前，先确认它能带来单智能体做不到的东西。

## 二、判据：什么时候单智能体就够

一个务实的过滤流程：

1. **任务能否用一条固定流程表达？** 能，就用工作流（链式、路由、并行），不必引入自主循环。
2. **上下文是否会互相干扰？** 若子任务需要完全不同的指令与资料，且混在一起会污染判断，拆分角色有收益。
3. **是否存在天然的并行或专业分工？** 例如检索、写码、评审三者用不同工具与标准，拆分可提升质量与速度。
4. **是否需要多轮自我纠错？** 反思（reflection）类模式在单智能体上也能实现，不必先上多体。
5. **收益是否大于通信成本？** 拆分意味着更多 token、更多往返、更多失败点。

如果你的答案是「全部都否」，那就写一条清晰的流水线。很多被包装成多智能体的系统，本质是 DAG 工作流，承认这一点能省掉大量调试时间。

下表把常见需求与推荐结构对应起来，供快速判断：

| 需求特征 | 推荐结构 | 主要代价 |
|----------|----------|----------|
| 步骤固定、顺序明确 | 链式工作流 | 灵活性低 |
| 需要按输入分流 | 路由工作流 | 路由判断本身可能出错 |
| 子任务相互独立 | 并行工作流 | 汇总与去重成本 |
| 需要自主决定步数 | 单智能体循环 | 循环可能不收敛 |
| 多专业视角互相校验 | 反思或辩论 | token 成本上升 |
| 超长、可递归拆解 | 层级编排 | 信号衰减、状态复杂 |

## 三、协作拓扑：四种常见结构

学界与工业界沉淀出若干可复用的结构，各有代价。

- **编排-工作者（orchestrator-worker）**：一个主智能体拆解任务，分发给若干工作者，再汇总结果。结构清晰，适合可并行的子任务。风险是主智能体的拆解质量成为全局瓶颈。
- **反思（reflection）**：执行者产出初稿，评审者给出反馈，执行者修订。Shinn 等人 2023 年的 Reflexion 工作展示了「用语言反馈做自我改进」的有效性。风险是评审者与被评审者同源，容易自我强化错误。
- **多体辩论（multi-agent debate）**：多个智能体独立作答后交叉质询。Du 等人 2023 年的研究表明，辩论能提升事实性与推理的可靠性。代价是成本随参与者数量线性乃至更高增长。
- **层级（hierarchical）**：团队套团队，适合超长任务。层级越深，信号衰减越严重，越需要严格的交接协议。

框架层面，AutoGen（Wu 等，2023）、MetaGPT（Hong 等，2023）、CAMEL（Li 等，2023）以及各类图式编排库都提供了实现。选框架时优先看**状态如何持久化、失败如何恢复、调用如何观测**，这三件事决定你能否把它带进生产。

## 四、交接契约：把「我以为你知道」写成协议

这是我们做 T-agent 时踩坑最多的部分。多智能体最容易在「我以为你知道」处翻车。解决办法是把每次交接都当作一次接口调用，强制携带结构化字段。

一份最小交接契约应包含：

```json
{
  "task_id": "唯一标识，便于追踪与去重",
  "from": "发起方角色",
  "to": "接收方角色",
  "goal": "一句话目标，可验收",
  "inputs": ["所需资料清单或引用"],
  "constraints": ["时间、格式、合规等硬约束"],
  "acceptance": ["验收条件，逐条可判定"],
  "output_schema": {"type": "期望输出结构"},
  "deadline": "时间预算",
  "fallback": "失败时的降级与上报路径"
}
```

关键在于三条纪律：

1. **验收条件前置**。写清「什么算完成」，避免把模糊期望丢给对方猜。
2. **允许拒绝**。接收方信息不足或越权时，应当返回结构化的「拒绝 + 原因」，而不是硬着头皮编一个结果。
3. **引用而非复制**。资料用引用传递，避免多份副本各自过期，产生「版本漂移」。

加州大学伯克利分校等机构 2025 年的多智能体失败分析（MAST 分类）把失败归为若干大类，其中相当一部分来自**规范与对齐缺失**，即智能体之间没对齐「做什么、做到什么程度」。契约正是对准这个病根的。

一个典型场景足以说明问题。研究型任务里，主智能体把「整理行业报告」交给写手，写手交回一份文采斐然但缺少来源标注的稿子。评审者按「语言质量」打分，给出高分放行。最终交付被用户指出「数据无出处」。复盘会发现：失败不在任何单个角色，而在两份契约——主智能体没有规定「必须标注来源」，评审者没有把「可核验」列入验收条件。**修补方式是把「可核验」写进 output_schema 与 acceptance，并让评审者据契约判定，而非凭印象打分。**

## 五、工具调用与 MCP：把能力标准化

函数调用让模型能输出结构化动作；MCP（Model Context Protocol，Anthropic 于 2024 年 11 月发布）进一步把「工具、资源、提示」的接入方式标准化为 JSON-RPC 协议，角色分为 Host、Client、Server。它的价值是收敛集成工作量：每个能力提供方实现一次服务端，任意兼容的宿主即可复用。

落地时的经验：

- **工具描述即接口文档**。名称、参数、返回值、错误码都要写清。模型对工具的理解，就来自这份描述。
- **工具要窄而稳**。一个「万能执行器」既是安全噩梦，也让模型难以选择。把能力切成语义清晰的小工具。
- **幂等优先**。涉及写操作的工具，尽量设计成幂等，或要求传入幂等键。
- **返回要有结构**。让工具返回结构化结果与明确错误，而非一大段自然语言。
- **安全默认关闭**。危险工具（删数据、转账、发消息）默认不授予，按需开启并加审批。

需要提醒：MCP 生态在权限控制、可信部署与服务器发现方面仍在快速演进，安全策略请以官方规范最新版本为准。

一个工具定义应当像一份严谨的接口文档。以查询库存为例：

```json
{
  "name": "check_inventory",
  "description": "查询指定 SKU 在指定仓库的可用库存，只读操作。",
  "parameters": {
    "type": "object",
    "required": ["sku", "warehouse"],
    "properties": {
      "sku": {"type": "string", "description": "商品编码"},
      "warehouse": {"type": "string", "enum": ["shanghai", "beijing"]}
    }
  },
  "returns": {
    "type": "object",
    "properties": {
      "available": {"type": "integer"},
      "updated_at": {"type": "string", "description": "库存更新时间"}
    }
  }
}
```

注意其中几个细节：`description` 说明「只读」，帮助上层做权限与审批判断；`enum` 收敛取值，减少无效调用；`updated_at` 让调用方能判断数据新鲜度。**把接口写严，模型的选择才会稳。**

## 六、记忆与状态：三本账要分清

多智能体系统里，「记忆」常被混为一谈。工程上应区分三类：

- **上下文记忆**：当前对话窗口内的信息，随会话结束消失。受 token 预算约束，需要摘要与裁剪。
- **长期记忆**：跨会话保存的事实与偏好，通常落在向量库或结构化存储，按需检索。
- **共享黑板**：同一任务中多个智能体共同读写的工作区。它是协作的核心，也是最容易产生竞态与脏读的地方。

共享黑板的设计要点：明确**写入权限**（谁能改哪块）、明确**版本**（冲突如何解决）、明确**可见性**（哪些角色能读到哪些字段）。把它当成并发编程里的共享内存来对待，而不是「大家随时写」。

关于记忆的一条冷峻提醒：**记忆会带来错误的复利。** 一次错误的总结被写进长期记忆，会在后续任务里反复污染判断。因此长期记忆需要可信度标注与定期清理机制。

## 七、权限与沙箱：最小权限是底线

一旦智能体能调用工具、读写文件、访问网络，安全问题就从「模型说错话」升级为「系统被执行了危险动作」。

- **最小权限**：每个角色只拿完成任务必需的权限。检索角色只读，写操作角色单独授权。
- **沙箱执行**：代码执行、浏览器操作这类高风险能力，放进隔离环境。轻量隔离可用 seccomp、命名空间；更强隔离可参考 gVisor、Firecracker 等微虚拟机方案。沙箱要限制网络、文件系统与 CPU/内存配额。
- **网络出口白名单**：默认禁止任意出网，只放行必要的域名，降低数据外传与命令回连风险。
- **凭据隔离**：用短期令牌替代长期密钥，遵循最小权限与可撤销原则。绝不把密钥写进提示词或可被模型读取的文件。
- **动作分级**：把工具分为「只读」「低风险写」「高风险写」。高风险动作强制人工审批（见第九节）。

一个最小沙箱配置应当显式声明四类限制——网络、文件、资源、时间：

```yaml
sandbox:
  image: "runner:minimal"
  network: "none"              # 默认断网
  allow_outbound: ["api.internal.example"]  # 需要时按域名白名单
  filesystem:
    read_only: ["/usr", "/lib"]
    writable: ["/work"]        # 仅工作目录可写
    no_exec: false
  resources:
    cpu: "1"                   # 单核
    memory: "512Mi"
    timeout_seconds: 60        # 超时强制终止
  credentials: "short_lived"   # 短期令牌，任务结束即失效
```

这份配置里，`network: none` 与域名白名单挡住了数据外传与命令回连，`writable` 限定保护了宿主文件系统，资源与超时限制防止单个任务打满机器，短期令牌降低了凭据泄露的损失半径。

安全界有一句老话：「防线要纵深」。多层防护哪怕每层都不完美，叠加起来也能显著降低事故概率。

## 八、可靠性与可恢复：假设它会失败

在分布式系统里，我们默认网络会抖动、节点会宕机。多智能体系统应当采用同样的心态。

- **幂等与去重**：每个任务带唯一 ID，写操作按幂等键去重，避免重试导致重复副作用。
- **检查点（checkpointing）**：在关键步骤保存中间状态，失败后从检查点恢复，而非从头再来。图式编排库通常内置这一能力。
- **补偿事务**：跨多个外部系统的操作难以回滚时，采用 Saga 式补偿——为每个正向操作设计对应的补偿操作。
- **超时与预算**：为每个子任务设时间与 token 预算，超限即中断并上报，避免单个环节无限拖垮全局。
- **重试分层**：区分「可重试」（网络抖动、限流）与「不可重试」（参数错误、权限不足）。指数退避加抖动是常规做法。
- **熔断与降级**：某工具持续失败时先熔断，改用降级路径，保护整体可用性。
- **确定性兜底**：关键判定尽量用规则或程序，把模型的角色收敛到「生成候选」，而不是「拍板定案」。

一句话总结这一节：**把不确定性关进可恢复的笼子里。**

## 九、人机回路：该停的地方要停

HITL（Human-in-the-Loop）不是不信任模型，而是把人的判断放在价值最高的位置。常见模式：

- **审批门（approval gate）**：高风险动作执行前暂停，等待人工确认或拒绝。
- **起草-确认**：模型生成草稿，人修改后再提交，适合对外沟通与内容发布。
- **异常升级**：置信度低、规则冲突、或涉及敏感领域时，自动升级到人工。
- **可中断与接管**：运行中的任务支持人工暂停、修正指令后继续，而非只能推倒重来。

设计要点是**把停机条件写进契约**，而不是依赖运行时的临场判断。哪些动作必须停、谁来批、超时未批怎么处理，都要事先定义。

从合规角度，HITL 也是应对《生成式人工智能服务管理暂行办法》等要求的重要手段——对可能影响用户权益的自动化决策，保留人工干预与复核通道。

## 十、可观测性与评估：如何衡量一个智能体系统

多智能体系统如果不可观测，调试就退化为猜测。

- **链路追踪**：把一次任务的所有步骤、工具调用、交接、重试串成一条轨迹，支持回放。
- **记录中间产物**：每次交接的输入输出、每次工具调用的参数与结果，全部落盘。这既是调试依据，也是评测数据来源。
- **指标分层**：任务级（成功率、成本、时长）、步骤级（工具成功率、重试率、拒绝率）、质量级（验收通过率、人工修改率）。
- **失败归因**：给失败分类（拆解错、检索错、工具错、交接错、越权被拒），才能针对性改进。
- **回归评测**：准备一批代表性任务，改动拓扑或提示后跑一遍，对比指标。

评测上，学界与业界正逐步形成共识：**端到端成功率高，未必代表过程可靠。** 一个靠运气蒙对的系统和一个稳定可复现的系统，必须用过程指标区分开。

一条合格的任务轨迹，应当能还原出「谁、在何时、收了什么、交了什么、调了哪些工具、是否重试」：

```text
trace task=ord-20261015-8842 status=failed duration=41.2s tokens=18234
  span 01 planner.split            ok    1.2s
  span 02 worker.retrieve          ok    3.4s  hits=6
  span 03 worker.draft             ok   12.7s
  span 04 critic.review            reject reason="missing_citations"
  span 05 worker.revise            ok    9.1s
  span 06 tool.submit_order        retry 2 attempts
  span 07 tool.submit_order        fail  error=permission_denied
  span 08 escalate.human           ok    0.3s
```

不用读完也能看出：失败根因是第 6、7 步的权限不足，而前五步的返工由「缺少引用」触发。**可观测的价值，就是让这种判断在一分钟内完成，而不是靠三个人开会回忆。**

## 十一、成本、安全与合规：三笔账一起算

- **成本**：多体的 token 消耗随参与者与轮次上升。要设总预算与单任务上限，避免「辩论到天荒地老」。用便宜模型做低价值步骤、贵模型做关键判断，是常见做法。
- **安全**：把提示注入当作常态威胁。任何来自外部的内容（网页、文件、用户输入、其他智能体）都可能夹带指令，必须与系统指令隔离，并对高风险动作做二次校验。
- **合规**：面向公众提供服务时，遵守内容安全、生成内容标识、数据与个人信息保护等要求；涉及自动化决策的，保留人工复核通道；留存必要的日志以备核验。

## 十二、一个最小可运行的编排骨架

概念讲完，给一个去掉框架依赖的伪代码骨架，把前文的约束落到结构上：

```python
def run_task(task):
    ctx = load_checkpoint(task.id) or new_context(task)
    budget = Budget(tokens=task.token_limit, seconds=task.time_limit)

    while not ctx.done:
        if budget.exceeded():
            return escalate(task, reason="预算耗尽", ctx=ctx)

        step = planner.next_step(ctx, budget.remaining())
        role = route(step)                     # 选择承接角色

        contract = build_contract(step, role)  # 交接契约
        if not role.can_accept(contract):      # 允许拒绝
            return escalate(task, reason="契约不可接受", ctx=ctx)

        if action.is_high_risk(step.action):   # 高风险动作
            if not await_human_approval(step): # 人机回路
                return abort(task, reason="审批拒绝", ctx=ctx)

        result = sandbox.run(step, idempotency_key=f"{task.id}:{step.id}")
        save_checkpoint(task.id, ctx, step.id)

        if result.failed and retryable(result):
            backoff_and_retry(step)
            continue
        if result.failed:
            compensate(step)                   # 补偿事务
            return escalate(task, reason=result.error, ctx=ctx)

        ctx.update(result, origin=role, version=ctx.version + 1)

    return verify(ctx, contract.acceptance)     # 按验收条件判定
```

这段骨架里，几乎每一行都对应前文的一条纪律：预算、路由、契约、拒绝、审批、幂等、检查点、重试、补偿、验收。**真正的工程量在这些护栏上，而不在提示词写得多么动人。**

对着这段代码，可以顺带记下几个反模式：

- **无限循环**：没有步数或成本上限，智能体互相「讨论」到天亮。
- **黑箱交接**：用自然语言传任务，接收方靠猜。
- **万能工具**：一个能执行任意命令的工具，等于把系统交给运气。
- **无检查点**：一旦失败全部重来，成本与不确定性翻倍。
- **静默失败**：调用失败被吞掉，上层以为成功。
- **权限过大**：检索角色拥有写权限，越权在所难免。
- **记忆无治理**：错误摘要被永久保存，污染后续所有任务。
- **全程无人**：高风险动作无人复核，出事才发现。

## 十三、结语：可靠来自约束，而非聪明

多智能体的浪漫想象是「一群聪明的模型自己协作」。工程现实是：**聪明会波动，约束才可复现。** 把交接写成契约，把工具标准化，把权限关进沙箱，把失败当作必然而非意外，把该由人拍板的地方留给人类——这些都不酷，但它们决定系统能不能活过第一个月。

> 君子慎独。——《礼记·中庸》

团队无人监督时的行为，取决于事先写下的规矩。

## 附录：多智能体上线前检查清单

- [ ] 确认任务无法用更简单的工作流完成，多智能体确有必要。
- [ ] 每个角色权限最小化，检索与执行分离。
- [ ] 交接契约包含目标、输入、约束、验收、输出结构、失败路径。
- [ ] 接收方具备结构化「拒绝」能力。
- [ ] 工具描述完整，写操作幂等或带幂等键。
- [ ] 高风险动作接入人工审批门。
- [ ] 代码与浏览器类能力运行在受限沙箱，默认断网、资源与时间受限。
- [ ] 关键步骤有检查点，跨系统操作有补偿事务。
- [ ] 有全局与单任务预算，超限可中断并升级。
- [ ] 全链路可追踪、可回放，失败可归类。
- [ ] 长期记忆有可信度标注与清理机制。
- [ ] 合规要求（内容安全、生成内容标识、自动化决策的人工复核）已落实。
