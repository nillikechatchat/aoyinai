## 缘起

做一个能独立完成数据分析任务的 Agent 时，我发现了单体的天花板：上下文越长越糊涂，工具一多就迷路，错了不知从哪改起。

在尝试构建一个能够独立完成复杂数据分析任务的单体 Agent 过程中，我经历了从乐观到失望的完整周期。最初，我设定了一个看似合理的目标：一个 Agent 能够理解业务需求，获取数据，进行清洗、分析、可视化，并最终生成报告。这个 Agent 拥有 20 多种工具，包括 SQL 查询、Excel 处理、统计分析和绘图等。

实践很快击破了理想。当上下文窗口达到 8000 tokens 后，Agent 开始出现明显的"上下文混淆"——它会在分析过程中忘记最初的数据范围，或者在生成图表时使用错误的数据子集。更令人头疼的是，当它犯错时，几乎无法定位问题根源。例如，有一次 Agent 生成了一个完全错误的统计结论，经过 3 小时的调试才发现，是因为它在第 5 步的数据处理中错误地过滤了 12% 的有效数据，而这个错误在后续步骤中被不断放大和掩盖。

「工欲善其事，必先利其器。」然而，当工具数量超过 10 个，单 Agent 的决策空间呈指数级增长，其表现反而急剧下降。我们的测试数据显示，当工具数量从 5 个增加到 15 个时，单 Agent 的任务完成率从 78% 下降到 32%，错误率从 15% 上升到 53%。

人类用分工解决了类似的问题——于是有了 T-agent。

## 核心设计

### 1. 角色即约束

每个 Agent 只配一个职责、一组有限工具。Planner 不碰工具，Worker 不改计划。约束产生可预测性。

在 T-agent 框架中，我们首先将复杂的任务分解为明确的角色，每个角色拥有严格的职责边界和有限的工具集。以数据分析任务为例，我们设计了四种核心角色：

- **Planner（规划者）**：负责理解业务需求，制定整体执行计划，分配任务给 Workers。它不执行任何具体操作，只拥有任务分解和任务分配工具。在我们的测试中，一个 Planner 可以高效管理 5-8 个 Workers 的协作。

- **DataFetcher（数据获取者）**：专门负责数据获取，包括数据库查询、API 调用、文件读取等。它只有 4-5 个数据获取相关工具，确保不会因为工具过多而迷失方向。

- **DataProcessor（数据处理器）**：专注于数据清洗、转换和预处理。它拥有数据操作相关的 6-7 个工具，但不负责分析或可视化。

- **Reporter（报告生成者）**：负责将分析结果整合为最终报告，包括可视化图表和文字总结。它拥有 3-4 个可视化工具和报告生成工具。

这种角色分离带来了显著的性能提升。在相同的数据分析任务测试中，T-agent 的任务完成率达到 85%，错误率控制在 8% 以下。更重要的是，当出现问题时，我们可以迅速定位到特定角色的责任范围，而不是像单 Agent 那样陷入混沌。

「君子务本，本立而道生。」明确的职责是协作的基础，也是系统可预测性的保障。

### 2. 消息即账本

所有协作通过结构化消息，全程留痕。出错时可以回放任意一步——像审计账本一样调试 Agent。

T-agent 的协作基于严格的消息传递机制，每条消息都采用统一的 JSON 结构，包含发送者、接收者、消息类型、时间戳和内容等字段。这种设计确保了所有交互都有完整记录，为调试提供了宝贵的数据。

在实际运行中，一次典型的数据分析任务会产生 50-200 条消息记录。例如，在一个中等复杂度的销售数据分析任务中，我们记录了以下关键消息序列：

```
1. Planner -> DataFetcher: "获取过去12个月的销售数据，包含产品类别、地区和销售额"
2. DataFetcher -> Planner: "数据获取完成，共12,345条记录"
3. Planner -> DataProcessor: "对销售数据进行清洗，去除异常值，补充缺失信息"
4. DataProcessor -> Planner: "数据处理完成，有效记录11,892条，异常值453条"
5. Planner -> Reporter: "按产品类别分析销售趋势，生成月度对比图"
6. Reporter -> Planner: "分析完成，发现电子产品销售额增长23%，而家居用品下降5%"
```

这种消息记录的价值在错误排查中尤为突出。有一次，我们的系统生成了错误的分析结论，通过回放消息记录，我们发现问题出在第3条消息中，DataProcessor 错误地将"异常值"理解为"缺失值"，导致数据被不当处理。而在单 Agent 系统中，这种错误往往需要数小时的人工调试才能发现。

消息记录还支持性能分析。通过统计各角色之间的消息传递频率和响应时间，我们发现 DataFetcher 和 DataProcessor 之间的交互占用了 40% 的总通信时间，这促使我们优化了数据传递机制，将批量数据获取和处理的效率提升了 35%。

「工欲善其事，必先明其迹。」完整的消息记录就是 Agent 协作的"足迹"，是调试和优化的基础。

### 3. 失败即路径

重试不是失败，是搜索。每条失败路径都会被记录，供 Planner 下次绕行。

在 T-agent 框架中，我们重新定义了"失败"的概念。每一次失败都被视为一次有价值的学习机会，其执行路径会被详细记录并存储在"失败库"中。Planner 在制定任务计划时，会参考这些历史失败路径，避免重复同样的错误。

我们的失败记录包含以下关键信息：
- 失败发生的角色和具体步骤
- 失败时的输入数据和环境状态
- 失败的具体错误类型和描述
- 失败发生时的上下文信息
- 建议的替代方案或参数调整

例如，在一次市场趋势分析任务中，我们的 DataFetcher 在调用第三方 API 时遇到了速率限制错误。这个失败被记录下来，并标记为"可恢复失败"。下次执行类似任务时，Planner 会自动调整数据获取策略，采用分批次请求或增加延迟的方式，避免了同样的错误。

另一个例子是，我们的 Reporter 在尝试生成超过 10 个类别的对比图时，因为图表过于复杂而失败。这个失败被记录后，我们调整了可视化策略，当类别超过 5 个时，自动改用分组堆叠图或小 multiples 布局，大大提高了可视化成功率。

通过这种方式，T-agent 系统的"自我修复"能力不断增强。我们的数据显示，经过 3 个月的运行和失败记录积累，系统的任务成功率从初始的 65% 提升到 88%，相同类型错误的重复率下降了 70%。

「祸兮福之所倚，福兮祸之所伏。」失败不是终点，而是通往成功的必经之路。

## 实践经验

在 T-agent 框架的实践中，我们总结了一套有效的角色设计原则。首先，每个角色的职责应当是"单一且完整"的，即一个角色应该能够独立完成其负责的子任务，而不需要依赖其他角色来完成自己的核心职责。例如，DataFetcher 应该能够独立完成数据获取并返回标准化的数据格式，而不是让 Planner 指导如何处理获取的数据。

其次，角色之间的接口应当标准化。在我们的实现中，所有角色之间的数据交换都采用统一的中间格式，确保即使工具或实现方式改变，角色间的协作仍然可以正常进行。这种标准化接口设计使我们在替换某个角色的具体实现时，不需要修改其他角色，大大提高了系统的可维护性。
