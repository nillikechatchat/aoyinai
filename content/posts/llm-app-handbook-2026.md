## 一、Demo 与上线之间，隔着一条河

很多团队第一次把大模型接进产品，都会经历同一种落差：演示当天惊艳，上线两周后事故不断。原因往往与技术含量无关，而在于我们默认「模型答得好」等于「系统能交付」。这两件事之间的距离，比参数规模之间的距离长得多。

本文尝试给出一条可走的路线：从模型的第一性原理出发，经过提示、结构化输出、检索增强（RAG）、评估、成本控制，落到安全合规与部署运维。写作原则只有一条：**凡结论，尽量落到公开论文、官方文档或可复现的工程常识上；凡涉及厂商价格、版本号、榜单排名这类易变信息，一律提示读者以官方公告为准，不作记忆性转述。**

孔子的学生子夏说「博学而笃志，切问而近思」。工程上的笃志，就是先把不确定的部分标出来，再谈方案。

## 二、第一性原理：模型到底在做什么

### 1. 自注意力与会话生成本质

2017 年，Vaswani 等人在《Attention Is All You Need》中提出 Transformer 架构，用自注意力替代循环结构，让序列建模可以大规模并行。今天的千亿级语言模型，绝大多数仍是这一家族的延续。

你需要在工程上记住三件事：

- **模型按 token 工作，不按「词」工作。** token 是子词或字节片段，中文一个字有时对应一个 token，有时是多个。上下文长度、计费、截断，全部以 token 计量。计费与上限请以各厂商官方文档为准。
- **生成是自回归的。** 模型一次预测一个 token，再把结果拼回去预测下一个。所以「输出越短越省钱、越快」是结构决定的，靠提示词哀求省不了多少。
- **自注意力的计算量随序列长度近似平方增长。** 这是长上下文成本高、延迟高的根源，也是「检索比塞满上下文更划算」这一工程直觉的来源。

### 2. 温度、top-p 与「幻觉」

推理时常见的采样参数有温度（temperature）、top-p、top-k。温度低，输出更确定、更保守；温度高，多样性上升、稳定性下降。做事实抽取、工单分类这类任务，通常把温度压低；做头脑风暴，可以适度调高。

必须接受一个事实：**语言模型的优化目标是「生成合理的下一个 token」，它天生追求流利，而非天生追求真实。** 这就是「幻觉」的来源。工程上不能靠信仰，只能靠约束：给它可核验的资料（RAG）、给它明确的拒答出口、在输出层做校验。

《大学》讲「知止而后有定」。让模型知道「不知道时该怎么答」，比逼它「什么都要答」更能收敛事故面。

### 3. 上下文预算与 token 经济学

把上下文窗口想象成一个固定容量的行李箱。系统提示、少样本示例、检索片段、对话历史、当前问题，全都要塞进去。工程上要养成两个习惯：

- **给每一类内容设预算。** 例如系统提示不超过某个 token 数、检索片段总数设上限、历史对话只保留最近若干轮并做摘要。超预算时按优先级丢弃，优先级最低的通常是最早的对话历史。
- **让预算可见。** 每次请求记录各部分 token 占用，才能在账单异常时快速定位是提示膨胀还是检索片段失控。

需要提醒的是：不同模型的分词器不同，同一段中文在不同模型下的 token 数并不相等。估算时以目标模型的官方 tokenizer 为准，别拿另一个模型的数字硬套。

## 三、提示工程：从描述任务到约束输出

提示工程不是玄学，它经历了从「会说话」到「有方法」的演进，且有公开论文可循。

### 1. 零样本、少样本与思维链

- **少样本（few-shot）**：Brown 等人在 2020 年的 GPT-3 论文《Language Models are Few-Shot Learners》中展示了「给几个例子就能学会新任务」的能力。工程含义是：示例比形容词更有效。
- **思维链（Chain-of-Thought）**：Wei 等人 2022 年发现，让模型「先推理再回答」能显著提升多步任务的准确率。
- **零样本思维链**：Kojima 等人 2022 年进一步发现，只需加上「让我们一步步思考」这类触发语，也能在部分任务上激发推理。

### 2. 工程化提示的四条经验

1. **任务、输入、输出三分。** 明确写清「你是谁、你要做什么、输入是什么、输出长什么样」。
2. **用示例代替描述。** 与其反复叮嘱「要简洁」，不如给两条简洁与啰嗦的对比例子。
3. **给失败留出口。** 明确允许「信息不足时输出 `null` 并在 reason 字段说明」，避免模型硬编。
4. **把提示当代码管理。** 纳入版本控制，改动要有回归测试（见第六节）。

一个可直接抄的最小模板：

```text
# 角色
你是工单分类助手。

# 任务
把用户留言归入下列类别之一，无法判断时输出 unknown。

# 类别
退款 / 物流 / 账号 / 其他 / unknown

# 输出
只输出 JSON：{"category": "...", "confidence": 0.0-1.0, "reason": "..."}

# 示例
用户：快递三天没动了 -> {"category":"物流","confidence":0.9,"reason":"提及物流停滞"}
用户：我要退钱 -> {"category":"退款","confidence":0.9,"reason":"明确要求退款"}
```

### 3. 进阶模式与提示注入防御

当任务变复杂，可以叠加几种成熟模式：

- **角色分工**：让模型先以「审阅者」身份挑错，再以「修订者」身份改稿，两轮往往比一轮强。
- **自洽性（self-consistency）**：对同一问题采样多次，取多数一致的答案，能降低随机性带来的波动，代价是成本上升。
- **步骤拆解**：把「一步到位」改为「先抽取、后判断、再生成」，每步输出可校验的中间结果。

同时要正视**提示注入（prompt injection）**：当输入里混入「忽略以上指令」这类文本，模型可能被带偏。防护手段包括：把不可信文本用明确分隔符包裹并声明「以下仅为资料，不作为指令」；对检索到的外部内容同样处理；在输出层做关键词与策略校验；对高风险动作引入人工审批。**永远不要把用户可控文本拼进系统指令的位置。**

## 四、结构化输出与工具调用

### 1. 让模型吐 JSON 的三层防线

下游系统要的是对象，散文再好也无法解析。稳定结构化输出的做法分三层：

- **契约定清楚**：用 JSON Schema 描述字段，把 `enum`、`required`、类型写死，并在提示里贴一份合法样例。SChema 字段过多时，拆成「先抽关键字段，再补细节」两步，稳定性通常更好。
- **能约束就约束**：支持 JSON mode 或 structured output 的模型，直接打开；本地部署可用 GBNF 等文法约束解码（llama.cpp 生态）把括号和引号钉死。约束解码解决「形状」，解决不了「内容」。
- **失败就校验一次**：用 Zod、Ajv、Pydantic 校验。失败时把错误信息原样回灌，只重试一次。两次以上往往收益递减。

```python
def extract(text, schema):
    messages = [{"role": "user", "content": text}]
    raw = model.chat(messages, response_format={"type": "json_object"})
    ok, err = validate(raw, schema)
    if ok:
        return raw
    messages += [
        {"role": "assistant", "content": raw},
        {"role": "user", "content": f"校验失败：{err}。请只返回修正后的 JSON。"},
    ]
    raw = model.chat(messages, response_format={"type": "json_object"})
    ok, _ = validate(raw, schema)
    return raw if ok else None
```

`None` 必须有业务兜底：记日志、进人工队列，切勿把半残对象写进数据库。

### 2. 工具调用与 MCP

函数调用（function calling）让模型从「输出文本」升级为「输出动作」。2023 年 OpenAI 公布函数调用能力后，主流厂商陆续跟进。它解决的问题是：模型不再需要你手工解析它想做什么，而是直接返回结构化的调用意图。

2024 年 11 月，Anthropic 发布开源的 **Model Context Protocol（MCP）**，用统一的 JSON-RPC 协议连接模型应用、数据源与工具，被业界比作「AI 的 USB-C」。其角色划分为 Host（宿主应用）、Client、Server（能力提供方），并在规范中定义了 tools、resources、prompts 三类能力。MCP 的价值在于把「N 个应用对接 M 个工具」的组合爆炸收敛为「各自实现一次协议」。需要提醒的是，围绕 MCP 的权限控制、可信部署与发现机制仍在演进，安全实践要参考官方规范的最新版本。

## 五、RAG：把外部知识接进来

检索增强生成（Retrieval-Augmented Generation）由 Lewis 等人在 2020 年 NeurIPS 论文中提出。核心思想朴素：**生成前先检索，把相关资料塞进上下文。** 它让模型能引用训练截止之后的信息，也降低了「张口就来」的概率。

一个完整的 RAG 流水线包含六个环节，任何一环偷懒都会体现在最终回答上。

### 1. 离线索引

- **解析与清洗**：PDF、HTML、扫描件先转成纯文本，去页眉页脚、去乱码。解析质量决定上限。
- **切分（chunking）**：按语义切，保留标题层级；块之间留少量重叠，避免答案被切在缝里。块过大引入噪声，过小丢失上下文，需要按文档类型调参。
- **嵌入（embedding）**：把文本编码成向量。中文场景常用多语种或中文优化模型（如各类 BGE、E5、M3E 系列），具体选型以公开评测与官方文档为准。
- **入库**：向量库承担相似度检索。常见选择有 FAISS（Johnson 等，2019，偏库）、Chroma、Qdrant、Milvus、pgvector（在 PostgreSQL 内做向量检索）。近似最近邻算法常用 HNSW（Malkov 与 Yashunin，2018）或 IVF 系列。

### 2. 在线检索与生成

- **召回**：用问题或改写后的问题做向量检索，取 top-k；可叠加关键词检索做混合召回。
- **重排（rerank）**：用交叉编码器或后期交互模型对候选做精排，把最相关的几块送给模型。重排常是「从能用」到「好用」的分水岭。
- **生成**：把检索片段与问题拼成提示，要求模型「仅依据给定资料作答，资料不足时明确说明」。

### 3. RAG 的常见失败模式

- **检索错**：召回不到正确资料。指标看召回率，手段是改切分、换嵌入、加混合检索。
- **检索对但没用上**：资料在上下文里，模型仍凭记忆作答。手段是强化指令、降低温度、在提示里显式编号引用。
- **资料本身过期或冲突**：这类问题要靠数据治理，模型无能为力。

记住一句工程守则：**RAG 的天花板是数据质量，不是模型参数。**

### 4. 混合检索与元数据过滤

纯向量检索擅长语义相近，但对专有名词、型号、编号这类「字面精确」的查询常常失灵。实践中常见做法是**混合检索**：向量召回与关键词召回（如 BM25）各取一批，融合排序后再重排。此外，给每个块打上元数据（来源、时间、部门、权限等级），在检索时先做过滤，既能提升相关性，也能实现**按权限隔离**——用户只检索自己有权限看的资料。这一条在企业和政务场景几乎是刚需。

### 5. 分块策略与常见参数

分块没有银弹，只有针对文档类型的取舍：

- **条款型文档**（合同、法规）：按条款边界切，保留编号，宁可块小也不要跨条款。
- **长文章**：按标题层级切，块内保留所属标题路径，方便模型理解语境。
- **表格与代码**：尽量整块保留，避免把结构化内容切碎。
- **问答对**：一问一答为一个块，命中率高。

参数上，块大小、重叠长度、top-k、重排后保留块数，都需要用评测集调，而不是照抄别人的配置。**任何「最优参数」都依附于你的数据和你的模型，脱离语境没有意义。**

## 六、评估：如何知道它变好了

没有评估，就没有迭代，只有「感觉变好了」。评估要分两层。

### 1. 离线评估

- **构造评测集**：从真实日志里抽样，人工标注标准答案，规模从几十条起步也能用。
- **任务指标**：分类看准确率、召回率；抽取看字段级准确率与完整率；生成看忠实度（是否基于资料）与相关性。
- **RAG 专项**：RAGAS 等框架把评估拆为忠实度、答案相关性、上下文精确率与召回率等维度，便于定位是检索的问题还是生成的问题。
- **LLM-as-judge**：Zheng 等人 2023 年的研究（MT-Bench / Judging LLM-as-a-Judge）表明，用强模型做裁判在多数场景与人工判断有较高一致性。使用时要注意位置偏差与冗长偏好，最好混合人工抽检。

### 2. 回归与线上

把提示词、检索参数、模型版本都纳入版本管理。每次改动跑一遍固定评测集，指标下降就不合并——这和软件工程的 CI 是同一回事。

线上则看四类信号：任务成功率、人工兜底率、用户反馈、成本与延迟。指标要能按提示版本、模型版本切片，否则出了问题无从归因。

## 七、成本与延迟：把账算清楚

大模型账单由三部分构成：输入 token、输出 token，以及你为体验付出的额外工程成本。真正可控的杠杆有这些：

- **缩短上下文**：无用的历史与样例直接删。上下文越长，成本与延迟越高。
- **提示缓存（prompt caching）**：多数主流厂商已支持对稳定前缀做缓存计费，把系统提示、长文档放在前缀能显著降本。具体支持范围与价格以官方文档为准。
- **输出结构化**：让模型只输出 JSON，禁止寒暄，能直接砍掉输出 token。
- **模型分级**：简单任务用小模型，复杂任务再上大模型。用路由器按难度分发是常见做法。
- **推理侧优化**：自建服务时，vLLM 的 PagedAttention（Kwon 等，2023，SOSP）通过分页管理键值缓存提升吞吐；量化（GPTQ、AWQ、GGUF 等）能降低显存占用；批处理提升利用率但会增加单请求延迟，需要权衡。
- **缓存语义结果**：完全相同的请求可直接命中缓存，不必再问模型。

延迟上要区分首 token 延迟（TTFT）与整体生成时间。前者影响「是否卡顿」，后者影响「是否等得住」。流式输出能改善体感，但不减少总计算量。

### 一个粗略的成本估算例子

假设一个问答接口，每次请求平均输入 3,000 token、输出 300 token，日请求 1 万次。那么日输入 3,000 万 token、输出 300 万 token。把这两个数乘以你所用模型的**官方单价**（输入价与输出价通常不同），再加上检索与嵌入的成本，就是理论下限。真实账单还会包含失败重试、评测调用与开发调试的消耗。

这个算式的价值在于暴露结构：**输出 token 往往比输入贵，长上下文任务里输入量才是大头。** 于是优化方向自然浮现——控制历史长度、启用提示缓存、把稳定前缀前置、输出只保留必要字段。具体单价随厂商与批次变化，务必以官方计费页为准。

## 八、安全与合规：中国场景的必答题

在中国境内向公众提供生成式人工智能服务，涉及一整套法规。以下是公开、可核验的要点，具体条款请以官方原文为准。

- **《网络安全法》**（2017 年 6 月 1 日施行）、《数据安全法》（2021 年 9 月 1 日施行）、《个人信息保护法》（2021 年 11 月 1 日施行）构成基础法律框架。
- **《互联网信息服务算法推荐管理规定》**（2022 年 3 月 1 日施行）针对算法推荐服务。
- **《互联网信息服务深度合成管理规定》**（2023 年 1 月 10 日施行）针对深度合成（含换脸、语音合成等）内容。
- **《生成式人工智能服务管理暂行办法》**：由国家互联网信息办公室等七部门于 2023 年 7 月 10 日公布，自 **2023 年 8 月 15 日**起施行。它对训练数据、内容安全、用户权益、备案与监督检查等作出规定，并确立「包容审慎、分类分级监管」的思路。
- **《人工智能生成合成内容标识办法》**：2025 年由四部门发布，自 **2025 年 9 月 1 日**起施行，要求对 AI 生成合成内容添加显式标识与隐式标识（如文件元数据），并对传播平台的核验责任作出规定。

工程落地上要落实几件事：

1. **内容安全**：输入与输出双向过滤，接入合规的内容审核能力，保留日志以备核验。
2. **数据合规**：训练与检索数据来源要合法，个人信息的收集与使用遵循「告知—同意」与最小必要原则。
3. **标识义务**：面向公众的生成内容按标识办法添加显式与隐式标识。
4. **备案与评估**：具备舆论属性或社会动员能力的服务，按相关规定履行算法备案与安全评估。
5. **免责边界**：对医疗、法律、金融等专业领域，明确「辅助参考」定位，不作确定性承诺。

需要强调的是，以上是公开法规的概括，实际业务应咨询法务并按最新官方口径执行。

## 九、部署与运维：可观测、可回滚

上线之后，系统的可靠性更多取决于工程而非模型。

- **可观测性**：记录请求、检索片段、提示版本、模型版本、token 用量与延迟。结构化日志加链路追踪（如 OpenTelemetry）能让事故定位从「猜」变成「查」。
- **限流与降级**：对模型调用设并发与超时上限；模型不可用时降级到规则或小模型，保证核心流程不整体瘫痪。
- **灰度与回滚**：提示、模型、检索参数都当配置管理，支持按流量灰度，出问题一键回滚。
- **幂等与重试**：对写操作加幂等键，重试要区分「可重试」（网络抖动）与「不可重试」（参数错误）。
- **评测门槛**：把离线评测集接入发布流程，指标不达标不放行。
- **人工兜底**：低置信度请求转人工，既保体验，也持续产出标注数据。

《左传》有言「居安思危，思则有备，有备无患」。上线不是终点，而是把「不确定」变成「可管理」的起点。

## 十、微调、蒸馏与模型选型

面对「效果不够好」，很多人的第一反应是微调。这里需要克制。经验上的决策顺序是：

1. **先改提示与检索**：多数「效果不好」其实是资料没给对或指令没写清。
2. **再考虑少样本与示例**：给对例子常常胜过训练。
3. **最后才动权重**：当任务风格高度固定、有足量高质量标注、且对成本或延迟有硬约束时，微调才划算。

需要动模型时，参数高效微调（PEFT）是主流起点，LoRA 与其变体（如 QLoRA）因显存友好被广泛采用。微调解决的通常是**格式、风格、领域用语**的稳定性，对「注入新知识」的效果有限，且知识会随时间过期——这也是 RAG 与微调常被组合使用的原因：微调管「怎么说」，检索管「说什么」。

**蒸馏**则是把大模型的行为迁移到小模型，用于降本或本地部署，代价是能力上限下降。选型时建议按任务难度分级，用路由器把简单请求交给小模型，把复杂请求留给大模型，在体验与成本之间取平衡。

> 工欲善其事，必先利其器。器之利钝，取决于任务，而非尺寸。

## 十一、结语：把信息沉淀为能力

这份手册没有承诺「一周精通」，因为大模型应用的本质是系统工程：模型是其中一个部件，提示、检索、评估、成本、合规、运维共同决定成品质量。任何单点堆料都换不来稳定。

如果只带走三句话：

1. **可核验优先**：涉及数字、价格、版本、法规，永远回到官方来源。
2. **评估先行**：先有评测集，再谈优化。
3. **约束优于祈祷**：能让系统校验的，别指望模型自觉。

> 博学之，审问之，慎思之，明辨之，笃行之。——《礼记·中庸》

## 附录：上线前检查清单

把下面这张单子贴在发布流程里，逐条打勾，能挡掉大多数低级事故：

- [ ] 评测集存在，且覆盖正常、边界、恶意输入三类样本。
- [ ] 提示词、检索参数、模型版本均已纳入版本管理与灰度发布。
- [ ] 结构化输出有 schema 校验，失败有兜底路径。
- [ ] 上下文各部分 token 占用可观测，超预算有降级策略。
- [ ] 输入与输出均过内容安全过滤，日志可追溯。
- [ ] 生成内容按法规要求添加显式与隐式标识。
- [ ] 模型调用有限流、超时与降级；写操作有幂等键。
- [ ] 低置信度请求有转人工通道。
- [ ] 成本有预算告警，异常用量能定位到提示版本。
- [ ] 隐私与数据来源合规性经法务确认。
